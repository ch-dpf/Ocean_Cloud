# 架构与部署

更新日期：2026-09-07。本文描述当前实现；Java 上传发布方案另见 [Java 后端接入说明](java-backend-integration.md)。操作步骤见 [主平台与子平台开发教程](platform-development-guide.md)。

## 1. 应用边界

主平台负责工作台、应用目录、应用配置和发布管理；子平台拥有自己的 React 根节点、业务布局、菜单和内部路由。

当前应用中心在同一标签页进入子应用，主平台与子平台共用外部 IP 和端口，只通过路径区分。子平台正式入口不使用 iframe，也不创建新标签页。

| 目录                          | 当前职责                                         |
| ----------------------------- | ------------------------------------------------ |
| `apps/portal`                 | 主平台页面、动态应用列表和管理入口               |
| `apps/geographic-information` | 内置地理信息工作区                               |
| `apps/marine-information`     | 内置海洋信息工作区                               |
| `apps/resources`              | 保留的本地开发示例，不在应用中心登记             |
| `packages/http`               | 各应用创建独立实例的 Axios 封装                  |
| `packages/ui`                 | 通用组件、Hash 路由 Hook 与运行配置读取          |
| `packages/theme`              | 构建期共享主题                                   |
| `packages/bridge`             | 保留的消息契约，常规整页子应用无需新增握手       |
| 同级 `Ocean_Cloud_Control`    | 应用记录、工程生成、源码构建、版本存储和静态入口 |

公共包在构建时复用，不是跨应用共享业务状态。禁止从其他 apps 目录导入业务源码。内置应用属于同一 npm workspace 仓库，新建应用则由模板生成完整独立工程。

## 2. 当前访问链路

开发时浏览器访问主平台 `http://localhost:5173`。主平台 Vite 将 `/api` 和 `/apps` 代理到内部控制服务，默认 `http://127.0.0.1:5180`。

| URL                                     | 行为                                                     |
| --------------------------------------- | -------------------------------------------------------- |
| `/#/`                                   | 主平台工作台                                             |
| `/#/applications`                       | 应用中心                                                 |
| `/#/application-management`             | 应用管理                                                 |
| `/#/application-recycle-bin`            | 回收站                                                   |
| `/#/apps/geographic-information`        | 主平台动态入口，读取应用配置后在当前标签页进入 launchUrl |
| `/apps/geographic-information/`         | 控制服务提供地理信息当前发布版本                         |
| `/apps/geographic-information/#/layers` | 子平台内部 Hash 路由，页面需由子平台实现                 |

`ApplicationRegistryProvider` 通过 API 读取应用目录，`ApplicationLaunch` 使用相对 `launchUrl` 导航。当前不再使用 `config/applications.ts` 的静态清单或 MicroApplicationFrame 容器。

子平台独立 Vite 调试端口为地理信息 5175、海洋信息 5176，模板生成应用默认 5190。它们只用于独立开发调试；应用中心始终读取发布产物，不自动转发到这些开发服务器。

## 3. 路由与运行配置

平台应用记录保存唯一 ID、名称、入口路由、启用/展示状态和当前版本。路由限定为 `/apps/单段标识`，允许修改且可与应用 ID 不同。

控制服务按路由定位应用，检查未删除、已启用及已发布，然后提供对应版本文件。无末尾斜杠的应用根地址重定向到带斜杠地址。

返回入口 HTML 时注入 `ocean-application-config` JSON 节点，提供 `basePath`、`portalUrl`、`name`。共享 `getApplicationRuntime()` 和 `useHashRoute()` 据此解析应用内部路径。返回地址采用 `/#/applications`，与统一入口保持同源。

后台构建使用 `--base=./` 生成相对资源路径；独立模板也配置相对 base。内置应用手工默认构建时应另外检查 base 配置和硬编码资源地址。

未知 Hash 路由由前端 NotFound 处理；未知应用或静态文件返回真正的 404。缺失 JS/CSS 不能回退到 HTML。未发布应用返回 503，停用应用返回 403，删除应用返回 404。隐藏只影响应用中心展示。

## 4. 工程创建、发布与持久化

当前控制服务使用 Node.js + TypeScript，运行数据默认位于自身 `var`：

- `database.json`：应用、版本、任务元数据。
- `projects/应用ID`：平台生成的独立源码工程与本地 Git 仓库。
- `builds/任务ID`：本次构建的源码快照。
- `generation/任务ID`：工程生成阶段目录。
- `releases/应用ID/版本ID`：发布产物。

创建应用会生成模板工程并初始化本地 master 仓库。内置地理信息与海洋信息继续使用 Ocean_Cloud 中对应工作区，不在 projects 下重复生成。

发布读取当前工程内容，创建快照，记录 Git HEAD 与源码摘要，执行锁文件依赖安装、TypeScript 检查及 Vite 构建。只有构建通过并保存产物后才切换当前版本，失败保持原版本。发布不是自动拉取远程分支，Git HEAD 也不能代表工作目录没有未提交修改。

任务当前全局串行，同应用拒绝重叠任务。状态持久化，服务重启时未完成任务标记失败；单数据目录有进程锁。该模型不等同于多实例任务调度。

回滚只切换当前发布版本，不回退源码。删除是可恢复删除，保留工程、版本、日志、ID 和路由；有排队或执行中任务时拒绝删除。恢复沿用原配置与当前版本。

入口 HTML 使用 no-store；历史产物保留供回滚与旧页面资源请求。当前静态文件缓存策略不能替代业务对固定文件名资源的版本管理；新增同名跨版本配置文件时，需要明确资源版本与缓存设计。

## 5. 主平台与子平台部署

主平台通过构建 `apps/portal/dist` 后更新主平台静态目录发布，不通过子应用发布按钮更新。公共包变更后，受影响的内置子应用需要重新构建和发布；生成工程的公共包副本需独立升级。

当前控制服务可统一托管主平台 dist、管理 API 和子应用产物。默认监听回环地址，主平台开发代理是目前浏览器的统一入口。

正式部署可使用 Nginx 作为唯一外部入口：主平台静态文件由 Nginx 提供，`/api/` 和 `/apps/` 转发给具备对应能力的后端。不能通过直接公开整个 releases 根目录绕过应用状态校验。

业务 API 需要另行接入。现有控制服务只实现应用管理接口，不自动承接地图、海洋数据等业务 API；开发和部署代理应按命名空间区分目标。

当前没有实际统一登录/RBAC、远程 Git 拉取、构建容器隔离、远程部署或多实例共享存储。正式网络部署需要落实相应能力；页面不增加工程状态横幅，能力与运维条件记录在文档中。

## 6. Java 上传发布的接入位置

Java 方案需要实现应用配置、multipart 包接收、校验与持久任务、版本启用/回滚、删除恢复和动态静态入口。前端需要增加上传入口并扩展类型与错误消息处理。

当前尚无上传 ZIP 的 API 和界面，不能只改代理地址就使用。源码构建与 ZIP 上传是不同发布来源，原有生成/构建能力需要保留、迁移或明确关闭，避免两套后端独立维护当前版本。

详细契约与 Nginx 示例见 [Java 后端接入说明](java-backend-integration.md)。

## 7. 验证重点

执行当前根命令 `npm run check` 验证格式、Lint、类型和全部工作区构建；独立生成工程另行构建。测试与辅助脚本仅本地保留，当前根 package.json 没有 npm test。

浏览器验证主平台进入应用、内部路由、刷新、返回和后退，全程保持当前标签页和统一外部地址。发布验证新版本生效、失败保留旧版本、回滚、删除恢复及接口/静态资源 404 边界。

备份与恢复要同时覆盖元数据和对应版本产物。生成工程是源码，不是缓存；更新服务程序或主平台文件时不清空运行数据。
